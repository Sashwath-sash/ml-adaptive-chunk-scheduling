Adaptive chunk scheduling: measured evidence

Real Linux worker processes execute a compiled C kernel. The application controller compares a fixed four-task baseline, cost-aware batching, and two trees that make a choice after a completed pilot. The Linux kernel scheduler is not modified.

What the tree actually learned

The mixed CART was trained on repeated whole-invocation candidate timings. Validation selected a depth cap of 2 and minimum leaf size 20 from 24 combinations. Its actual split features are: prime_fraction, remaining_cost_cv. None are live pilot measurements in this selected model. This is an observed result, not a claim that the pilot was useful for these tasks.

The measured-only ablation was given just six real pilot timings. Validation selected a depth cap of 1; both leaves predict fixed four. A short pilot cannot observe the hidden expensive task near the end, so it cannot reliably choose early cost ordering by itself.

Protocol and limits

Training uses seeds 6001–6004 at two workload scales; validation uses 7001–7003 at an unseen middle scale; final testing uses 8001–8010 at another unseen scale. Every method runs on the same 192 tasks with two workers, and method order is shuffled within each group. The primary timer includes feature extraction, pilot execution, inference, batching, pool startup, dispatch, and teardown. Offline fitting is excluded because the saved model is reused.

These are generated workloads on one WSL2 machine. The late-heavy pattern was deliberately constructed to stress a costly task near the queue tail; it is not a production trace. The pilot is a blocking round, and the selected tree does not show a general speedup. Numerical differences of a few percent require more hosts and longer runs before generalization.
